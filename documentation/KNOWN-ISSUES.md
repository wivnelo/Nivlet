# 已知问题与观察项

更新：2026-10-21。以下区分源码修复、已发布版本与运行验证边界。

## P2 · 重新授权后的状态恢复（已处理并完成本机安装验证）

2026-10-21：ARM 本机从 ad-hoc 切换到 Developer ID 公证候选后，用户移除旧权限并重新授权；原进程仍报告未开启，正常退出重开后检测已开启，用户确认其他功能正常。因此该现象不能归因于 Intel 架构。

本轮源码修改：统一窗口保存、配置导入、窗口操作与直接粘贴的权限判断；系统信任值为 false 时也执行 Finder 跨进程只读探测；系统信任与实际访问不一致时提供重开提示，仍保持拒绝受保护操作，不仅凭 AXRole 宣称键盘注入已恢复。接入 Runtime 的权限变化回调刷新界面。未授权区域仅补充退出重开文字引导，按用户要求移除额外退出按钮；普通退出仍沿用保存/放弃/取消的草稿保护，并明确非持久化历史退出后清空。

边界：不能强制刷新 macOS 的进程级授权状态，也没有证明所有情况均可免重启恢复。没有自动退出、修改 TCC 或反复删除授权。本机已切换到重新签名公证的 1.0.6 / Build 51，启动与权限重新检测通过。Build 49 → 50 沿用授权，未改 TCC 或移除重加权限。工具未主动撤销权限；用户随后重新操作授权后，旧进程曾显示状态不同步，重启至 Build 51 后恢复，不宣称已消除系统级重启要求。

后续正式升级应保持相同 Bundle ID、开发者 Team 和兼容的 designated requirement；公证不是权限保留机制。ad-hoc 到 Developer ID 的迁移可能需要重新授权，稳定正式签名升级通常可沿用，本轮已验证本机两个不同 Build 的直接替换可沿用；仍不能保证其他系统、用户重置权限或签名身份变化时不需要重授。

### 2026-10-14 历史核查


用户在 Intel Mac 替换新版后，从系统权限列表移除旧 Nivlet 并重新添加当前 App，仍需彻底退出重开才恢复；ARM 本机此前重新添加后立即可检测到授权。两台机器的系统版本、重启前实际功能与底层检测值尚未对照，不能确认是 ARM/Intel 差异。

代码核查：两架构使用相同权限逻辑，无按架构分支；每次检测直接调用 AXIsProcessTrustedWithOptions，不是 Nivlet 保存了旧布尔值。但实际 Finder 跨进程探测只在系统先返回已授权时执行，系统返回旧 false 时会跳过探测；这是一处可能的检测盲点，尚不能认定是本次根因。底层 Runtime 还记录部分事件监听可能要授权后重启才能恢复。

后续最小验证：记录两机 macOS、Nivlet 版本；在重新添加权限后/退出重开后分别记录系统信任值、Finder AXRole 探测结果、窗口功能是否可用。先区分显示未刷新与实际功能未恢复，再决定改检测或提供明确的重启引导。禁止假报已授权、绕过 TCC 或自动改系统权限。

本项按用户决定列为 P2，不阻塞本次发布，不影响当前已完成的重复提示修复；无数据丢失证据。仍为 ad-hoc 分发，没有 Developer ID 或 Apple 公证。
